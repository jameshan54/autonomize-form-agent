# Intelligent Form Agent 구현 계획

## 1. 목표와 범위 기준

이미지 양식에서 정보를 추출하고, 단일 문서 QA·요약과 여러 문서 종합 분석을 제공한다. 핵심 파이프라인을 먼저 구현하고 실제 원본과 대조해 검증한 뒤, 간단한 Streamlit UI를 연결한다.

- 요구사항 기준: [Machine Learning Assignment.pdf](../assignment/Machine%20Learning%20Assignment.pdf), 전체 2페이지.
- 데이터 검토 범위: [data/raw/project_data/](../data/raw/project_data/)의 PNG 11개.
- `assignment/job-description.md`는 읽지 않았으며 요구사항에 반영하지 않는다.
- 이 문서는 계획이다. 아래 체크리스트는 구현 완료를 의미하지 않는다.
- 본격적인 정확도 평가, 실패 유형 분석, 개선 전후 비교, 비용 대시보드와 추가 인프라는 추후 확장으로 둔다.
- 실제 원본 대조 검증과 모델 호출별 처리 시간·API 제공 토큰 사용량 기록은 이번 범위에 포함한다.

## 2. 필수 구현 범위

### 과제 필수 기능과 제출물

- [ ] 이미지 양식의 정형 정보와 비정형 정보 추출.
- [ ] 단일 문서 QA.
- [ ] 단일 문서 요약.
- [ ] 여러 문서를 종합한 답변과 분석.
- [ ] 기능 설명, 환경 설정, 단계별 실행 방법, 예제 질문과 기대 결과를 포함한 README.
- [ ] 단일 문서 QA·단일 문서 요약·여러 문서 종합 답변의 필수 데모 각 1개 이상.
- [ ] `requirements.txt` 또는 `environment.yml`로 의존성 명시.
- [ ] 핵심 소스, 데이터, 테스트, 문서를 논리적으로 분리한 저장소.
- [ ] 최소 설정으로 전체 흐름을 실행할 수 있는 저장소 또는 압축 폴더.

PDF는 `/src`, `/data`, `/notebooks`, `/tests`, `/docs`를 논리적인 구성 예시로 제시한다. 실험이 필요할 때 노트북을 추가하며, 이번 목표를 위해 별도 모델 학습이나 실험 기능을 만들지는 않는다. 스크린샷·로그·짧은 시연 영상은 선택 사항이다.

### 사용자 요청으로 포함하는 Streamlit UI

PDF에서 UI는 선택 사항이지만 이번 구현 범위에는 포함한다. 핵심 파이프라인과 분리하고 README에 별도 실행 방법을 설명한다.

- [ ] 제공 문서 선택 또는 이미지 업로드.
- [ ] 원본 이미지와 추출 결과 확인.
- [ ] 질문 입력, 답변과 출처 표시.
- [ ] 단일 문서 요약 확인.
- [ ] 여러 문서 선택과 종합 질문.

초기 입력 범위는 제공된 PNG를 포함한 이미지 양식이다. 업로드 지원 이미지 형식을 명시하며, 다중 페이지 PDF 업로드 등은 별도 필요성을 검토한 뒤 제안한다.

## 3. 실제 데이터 특징과 제약

- PNG 11개 모두 2480×3509 크기이며 파일 UUID와 내용 해시가 각각 다르다.
- 모두 같은 Texas 의료서비스 사전승인 요청 양식이다.
- 환자 정보, 요청·서비스 제공자 정보, 긴급 여부, 서비스·진단 표, 치료 종류·횟수·기간 등이 포함돼 있다.
- 파일명에는 `page_1`이 7개, `page_2`가 4개지만 이미지 내부에는 모두 `Page 2 of 2`가 인쇄돼 있다.
- 같은 UUID의 다른 페이지는 제공되지 않았다. 현재는 이미지 한 개를 제공된 문서 한 건으로 취급한다. 서로 다른 UUID의 파일을 임의로 합치거나 누락 페이지 내용을 추정하지 않는다.
- 일부 발급기관명은 지워지거나 훼손돼 있다. 빈칸, 판독 불가, 체크 표시와 인쇄 노이즈를 구분해야 한다.
- 서비스·진단 설명에 짧거나 불완전한 문구가 있다. 의료 코드를 근거로 원문에 없는 설명을 임의로 완성하지 않는다.
- 자유 텍스트와 섹션 원문은 보존하되, 긴 서술형 임상 기록은 확인되지 않았다. 이 데이터만으로 긴 서술문 추출 성능이나 다양한 양식에 대한 일반화 성능을 검증했다고 주장하지 않는다.
- 검토 폴더에 정답 라벨이나 별도 텍스트 파일은 없다. 소규모 수동 기대값을 원본에서 작성해야 한다.

PDF와 PNG 11개는 모두 열어 확인했다. 일부 이미지의 훼손된 글자는 확정 판독하기 어렵다. `data/project_data.zip` 내부는 별도로 검사하지 않았다.

## 4. 아키텍처

처리 흐름은 다음과 같다.

> 이미지 입력 → 문서 식별 → 정보 추출 → 공통 문서 데이터 → QA·요약·종합 분석 → CLI 또는 Streamlit UI

### 구성과 책임

- **입력·문서 관리:** 원본 파일, 문서 ID, 파일명 페이지 번호, 인쇄 페이지 정보를 구분해 보존한다. 업로드 입력도 동일한 처리 경로를 사용한다.
- **추출:** 구조화 필드, 체크박스 상태, 서비스 표의 행, 자유 텍스트와 섹션별 근거를 추출한다.
- **공통 데이터 형식:** UI와 무관한 직렬화 가능한 문서·근거·답변 형식을 정의한다. 추출 원문과 정규화 값을 구분한다.
- **QA:** 선택 문서의 구조화 데이터와 추출 원문을 근거로 답한다. 정보가 없거나 판독할 수 없으면 이를 명시한다.
- **요약:** 요청 성격, 주요 서비스와 진단, 제공자, 일정·횟수, 중요한 누락 정보를 간결하게 정리한다.
- **종합 분석:** 선택한 문서의 공통점·차이점·조건별 건수를 근거와 함께 제시한다. 명시적 건수와 합계는 추출 데이터를 코드로 집계하고 모델은 이를 설명한다.
- **모델 호출 공통부:** 모델 연결, 호출별 처리 시간과 사용량, 실패·재시도 기록을 담당한다.
- **CLI·UI:** 동일한 핵심 함수를 호출한다. Streamlit 코드는 입력, 상태 관리와 결과 표시에 집중한다.

추후 평가 코드가 추출·QA·요약·종합 분석 함수를 UI 없이 직접 호출할 수 있도록 한다. 핵심 로직은 Streamlit 세션이나 화면 상태에 의존하지 않는다.

### 추출 방식 초기 제안

이미지와 체크박스를 함께 읽어야 하므로 이미지 입력을 지원하는 모델을 이용한 추출을 초기안으로 제안한다. 모델 제공자와 구체적인 모델은 아직 확정하지 않았다. 별도 OCR 엔진이나 검색 인프라는 실제 결과에서 필요성이 확인되면 제안하며 자동으로 범위에 추가하지 않는다.

현재 데이터가 같은 양식이라는 이유만으로 문서 이해 전체를 특정 좌표에 고정하지 않는다. 공통 데이터 형식에는 양식별 추가 필드와 자유 텍스트를 보존할 여지를 둔다.

### 데이터와 출처 원칙

- 문서 ID, 원본 파일, 제공된 페이지와 인쇄 페이지 정보를 보존한다.
- 구조화 필드, 반복되는 서비스·진단 행, 섹션별 자유 텍스트를 구분한다.
- 식별번호와 의료 코드는 문자열로 보존한다.
- 원문과 정규화 값을 구분한다.
- 빈칸·판독 불가·체크되지 않음을 서로 다른 상태로 표현한다. 문서에 표시된 `Unknown` 선택지도 판독 실패와 구분한다.
- 출처는 최소한 파일명, 페이지, 섹션, 필드 또는 표의 행, 근거 원문까지 연결한다.
- QA는 요약만을 근거로 수행하지 않는다. 추출 원문과 구조화 데이터를 함께 사용한다.
- 없는 내용을 보완하거나 요청 양식만으로 승인 완료·치료 시행을 단정하지 않는다.

## 5. 단계별 작업 체크리스트와 검증 방법

### 1단계: 문서 식별과 데이터 형식 확정

- [ ] 입력 11개를 문서별로 목록화한다.
- [ ] 문서·필드·표·근거·답변의 공통 형식을 정의한다.
- [ ] 원본을 보고 소규모 수동 기대값과 검증 질문을 작성한다.
- [ ] 정상 값, 빈칸, 훼손된 값, 체크박스, 서비스 표 사례를 검증 대상에 포함한다.

**검증:** 서로 다른 문서가 섞이지 않는지, 파일명 페이지와 인쇄 페이지를 혼동하지 않는지 확인한다. 기대값은 모델 출력에서 복사하지 않고 원본 이미지와 대조해 확정한다.

### 2단계: 추출 파이프라인 구현·검증

- [ ] 대표 문서로 이미지 입력부터 공통 문서 데이터 생성까지 연결한다.
- [ ] 환자·제공자 필드, 체크박스, 서비스·진단 표, 자유 텍스트를 추출한다.
- [ ] 빈칸과 판독 불가 상태를 보존한다.
- [ ] 출력 형식 검증과 모델 호출 기록을 연결한다.
- [ ] 11개 전체를 처리하고 원본과 결과를 대조한다.

**검증:** 주요 필드, 표의 행 연결, 코드·날짜, 체크 상태, 자유 텍스트 누락을 실제 이미지와 나란히 비교한다. 지워진 기관명이나 불완전한 설명을 생성하지 않는지 확인한다. JSON 형식이 유효한 것만으로 통과시키지 않는다. 확인한 오류와 조치 결과는 간단한 검증 기록으로 남긴다.

### 3단계: 단일 문서 QA 구현·검증

- [ ] 선택 문서의 추출 데이터와 원문 근거로 답변한다.
- [ ] 답변에 출처를 연결한다.
- [ ] 정보 없음과 판독 불가를 설명한다.
- [ ] 단일 필드, 표의 여러 항목 연결, 체크박스, 답이 없는 질문을 검증한다.

**검증:** 답변과 출처를 모두 원본과 대조한다. 예를 들어 긴급 체크가 있어도 긴급 사유 칸이 비어 있으면 이유를 생성하지 않아야 한다. 다른 문서의 정보가 섞이지 않아야 한다.

### 4단계: 단일 문서 요약 구현·검증

- [ ] 요청 성격, 주요 서비스와 진단, 제공자, 일정·횟수, 중요한 누락 정보를 요약한다.
- [ ] 요약에서 사용한 근거를 추적할 수 있도록 한다.
- [ ] 문서에 없는 사실을 추가하지 않도록 처리한다.

**검증:** 요약의 각 사실을 원본과 대조하고 주요 내용 누락을 확인한다. 요청 상태를 승인 완료나 치료 시행으로 바꾸지 않는지, 불완전한 진단 문구를 임의로 확장하지 않는지 검사한다.

### 5단계: 여러 문서 종합 분석 구현·검증

- [ ] 선택 문서만 분석에 포함한다.
- [ ] 공통점·차이점·조건별 건수를 답한다.
- [ ] 집계가 필요한 명시적 값은 코드로 계산한다.
- [ ] 문서별 근거와 누락값을 답변에 반영한다.

**검증:** 수동 집계와 결과를 비교한다. 분모, 누락값 처리, 중복 집계 여부와 출처를 확인한다. 선택하지 않은 문서의 정보가 답변에 포함되지 않아야 한다. 개별 요약을 나열하는 데 그치지 않고 질문에 맞는 종합 결론을 제공하는지도 확인한다.

### 핵심 파이프라인 검증 완료 조건

- [ ] 11개 문서의 추출 결과를 원본과 대조했다.
- [ ] QA·요약·종합 분석을 UI 없이 실행할 수 있다.
- [ ] 대표 검증 사례에서 답변과 출처를 확인했다.
- [ ] 알려진 오류는 수정하고 영향받는 사례를 재검증했으며, 남은 판독 한계는 명시했다.
- [ ] 모델 호출별 시간·토큰 기록이 남는다.

이 조건을 확인한 다음 UI를 연결한다. 소규모 검증 결과를 전체 정확도나 일반화 성능으로 표현하지 않는다.

### 6단계: Streamlit UI 연결·검증

- [ ] 문서 선택·이미지 업로드를 연결한다.
- [ ] 원본 이미지와 추출 결과를 표시한다.
- [ ] 질문 입력, 답변과 출처를 표시한다.
- [ ] 요약을 표시한다.
- [ ] 여러 문서 선택과 종합 질문을 연결한다.
- [ ] 문서별 상태와 기존 결과 재사용을 관리한다.

**검증:** CLI와 UI가 동일한 핵심 함수를 사용하는지 확인한다. 문서 변경 시 이전 문서의 답변이 남지 않아야 한다. 단순 화면 재실행으로 모델이 불필요하게 다시 호출되지 않아야 한다. 제공 파일 선택과 같은 이미지 업로드가 동일한 처리 경로를 사용하는지 확인한다.

### 7단계: README·데모·제출물 검증

- [ ] 기능, 구현 범위와 알려진 한계를 README에 기록한다.
- [ ] 의존성 설치, API 설정, 핵심 파이프라인 실행 방법을 설명한다.
- [ ] UI 실행 방법을 별도로 설명한다.
- [ ] 필수 데모 3개의 입력, 질문 또는 작업, 기대 결과, 실제 실행 결과를 기록한다.
- [ ] README의 순서대로 최소한의 새 환경에서 전체 실행을 확인한다.
- [ ] 저장소 또는 압축 폴더 형태의 제출 구성을 확인한다.

## 7. 모델 호출별 시간·토큰 기록

추출·QA·요약·종합 분석이 공통 모델 호출부를 사용하도록 하고, 로컬 JSONL로 간단히 기록한다.

- 실행 ID와 호출 ID.
- 작업 종류와 관련 문서 ID.
- 모델명, 프롬프트 버전과 스키마 버전.
- 시작 시각과 호출 소요 시간. 소요 시간은 단조 증가 시계를 사용해 측정한다.
- 성공·실패 상태, 오류 유형과 재시도 번호.
- API가 제공한 입력·출력·전체 토큰 및 추가 usage 항목.

API가 제공하지 않은 사용량은 `null`로 남기며 추정값으로 채우지 않는다. 재시도는 별도 호출로 기록한다. 캐시로 결과를 재사용한 경우는 실제 API 호출과 구분한다. 호출별 시간은 전체 문서 처리 시간과 동일한 지표로 표현하지 않는다. 실행 메타데이터 로그에는 문서 원문이나 질문·답변 전체를 불필요하게 복제하지 않는다.

이번에는 토큰을 금액으로 환산하거나 실제 청구 비용이라고 표시하지 않는다. 추후 모델별 요율과 기준 날짜를 적용해 추정 비용을 계산할 수 있다. 별도 로깅 서버나 모니터링 인프라는 도입하지 않는다.

## 8. 추후 확장 제안

아래 항목은 이번 필수 구현 범위에 포함하지 않는다. 필요성과 효과를 설명하고 제안한 뒤 범위를 결정한다.

- **정답셋과 정확도 평가:** 검증 문서·질문이 충분히 모이면 추출 필드, QA 답변, 출처 정확도와 요약 누락을 반복 측정한다.
- **실패 사례 분류:** 체크박스 오인식, 표의 행 혼동, 판독 불가, 근거 없는 답변 등 반복되는 실패의 원인을 분석한다.
- **개선 전후 비교:** 동일한 입력과 기대값으로 모델·프롬프트·스키마 변경 효과를 비교한다. 이번 버전 기록과 독립된 핵심 로직을 재사용한다.
- **처리 시간·비용 분석:** 호출 로그가 쌓이면 작업별 지연과 토큰 사용량을 분석하고, 기준 요율을 적용한 추정 비용을 추가한다.
- **OCR 병행 또는 이미지 전처리:** 실제 추출 오류에서 별도 OCR, 확대·영역 분할 등의 필요성이 확인될 때 검토한다.
- **검색·벡터 DB:** 문서 수나 문맥 길이가 커져 전체 선택 문서를 직접 처리하기 어려워질 때 검토한다.
- **다양한 양식·장문·다중 페이지 지원 검증:** 추가 데이터가 확보되면 현재 데이터로 확인하지 못한 입력 유형을 검증한다.
- **평가 대시보드와 추가 인프라:** 반복 평가와 운영 요구가 생겼을 때 검토한다.

현재는 필수 기능과 간단한 UI를 완성하고, 실제 문서 대조 결과·호출 기록·UI와 분리된 핵심 로직을 남기는 데 집중한다.
